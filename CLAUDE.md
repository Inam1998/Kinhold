# Kinhold: start here

Native Android app (Kotlin, Jetpack Compose) for building and keeping a private family tree. Working name and brand: **Kinhold**. App ID `com.inamibrahim.kinhold` (permanent once published). Owner GitHub: Inam1998, repo `Kinhold`.

The full plan, research and monetization are in `docs/PLAN.md`. Read it before starting a feature.

## What it is
A family tree app for people who want to keep their own tree without a subscription. It is free with light ads plus a one-time Pro unlock. It is not a records search service and has no DNA or historical record database. The gap it targets: the big apps (Ancestry 4.0, MyHeritage 3.8, FamilySearch 3.5, all 10M+ downloads) are disliked for price, billing traps, lost trees and a clumsy tree view, while the small apps are basic.

## Rules that must hold
- **Look:** follow `D:\Android Projects\DESIGN-SYSTEM.md` (dark-first navy, cards, big radii, Inter font, gradient glow, floating nav). Only the accent differs: Kinhold is green. Reference code: `ui/Theme.kt` and `ui/Components.kt`.
- **Design for all phones:** old and slow phones count as much as new ones (minSdk 26). Bound memory per item, keep main-thread work independent of tree size, and say in replies what was reasoned for weak phones rather than measured.
- **Never lose a tree.** Data safety is the selling point. Local storage first, atomic saves, automatic backup, GEDCOM and full-file export. Any change that touches stored data needs a migration and a test.
- **Permissions only when a feature needs them,** each disclosed in the store listing: camera (scan), microphone (stories), contacts (import), internet (ads, only when ads are added). Check the manifest before each release.
- **No face recognition** in version 1 (privacy and policy risk).
- **Ads never appear** over the tree view, while editing a person or while recording. Pro removes ads.
- **Every new feature gets a page in the in-app Help guide** in the same change, with its limits stated (`model/HelpGuide.kt`: add a `HelpTopic` and a `HelpPage`; `HelpGuideTest` fails if a topic has no page, if a page does not state its limits, or if the Privacy page says there is no internet permission while the manifest asks for one). When a feature changes, change its page in the same change.
- Commit and push only when the owner asks. Work on a branch, not `main`. Do not put assistant or AI mentions in commits, code or docs.
- Keep this file and `docs/PLAN.md` current when a feature lands.

**Events and sources (0.1.0, database version 3, backup format version 3):** `model/Events.kt` has `PartialDate` (year, month, day, each optional; a month needs a year, a day needs a month), `EventKind` (baptism, burial, occupation, military, residence, immigration and more, plus couple kinds marriage, engagement, divorce, annulment, and Other with a name), `Event`, `Source` (title, citation, note; plain text, no scans) and the limits (500 events per person or couple, 50 sources per event or person, text cut at set lengths). Birth and death keep `born`/`died` years and gain optional month and day columns. Other events are rows in `event` (owned by a person, or by a couple via a composite key to `partnership`), citations rows in `source`; both cascade on delete. `Family` keeps only a small `CoupleInfo` per couple (earliest marriage date, ended or not), so `Family.spousesInOrder` orders spouses by marriage date, then birth year, then id (used by the layout and the add-child chooser), and `Relatives` ignores spouses whose partnership has a divorce or annulment. Events are read per person (`FamilyRepository.details`), never for the whole tree. Migration: `FamilyDb.onUpgrade` for version below 3 adds the four columns and the tables (tests: `EventsDbTest.aVersionTwoDatabaseIsUpgradedWithoutLosingAnything`, and the old version-1 test in `PhotoTest`). The safety copy, Undo restore and Delete + Undo carry events and sources. GEDCOM: full dates and events (BAPM, BURI, OCCU, RESI, EVEN with TYPE and so on, MARR, DIV, ENGA, ANUL on couples) and source citations (records with TITL, citations with PAGE and NOTE) are read and written; `GedcomReport` now counts only what is dropped (`datesSimplified` for about/between dates, SSN, ordinances and contact lines as events, family-level citations, events over the limit or on a one-parent family) and says how many events and citations were kept. Citations on a birth or death become person-level sources with an "About the birth." note. **GEDCOM import and export (0.4.0, checked on the S22):** `model/Gedcom.kt` (pure Kotlin) reads GEDCOM 5.5, 5.5.1 and the common parts of 7.0, and writes 5.5.1 (UTF-8, CR LF, HEAD with SUBM, lines under 255 characters using CONC and CONT). Reading is forgiving: any line ending, blank or junk lines skipped, UTF-8 with or without BOM, UTF-16 (BOM or not), "ANSI"/ASCII/ANSEL read as Windows-1252 (ANSEL accents in very old files can come out wrong), unmarked non-UTF-8 files fall back to Windows-1252, `@@` unescaped, notes as inline text or as separate NOTE/SNOTE records, `NAME` with `/surname/` and suffix or `GIVN`/`SURN`, dates in every common style reduced to the first year found (`BC` dates give no year), `FAMC` honoured when a family does not list the child, `@VOID@` ignored, several marriages kept as several partnerships. What is not kept is counted in a `GedcomReport` and shown before import: dates with more than a year, events (marriages, jobs, residences and so on), source citations, photos and files, other details, and links to people missing from the file. Export writes one FAM per couple and per group of children with the same parents (couples without children and single parents are kept; a child with more than two parents gets one FAM per parent). Import asks Add (renumbers people, keeps everyone already there; people in both appear twice) or Replace, both writing the safety copy so "Undo the last restore or import" works; an empty tree just offers Import, from the start screen or the Backup screen. Tests: 27 GEDCOM tests (hand-written sample with two marriages, every date and name style, encodings, damaged and random files never crash, 300-person round trip, difficult text, 3,000 people under 3 s) and 2 more on-phone tests (add import with overlapping ids and undo; GEDCOM through the database). Totals: 67 JVM and 18 on-phone tests. By hand on the S22: imported an Ancestry-style file through the picker (dialog counts matched the file), checked the tree, exported it again (`kinhold-2026-11-07.ged` keeps its extension). Test files left on the phone in Downloads: `test-tree.ged` (11 invented people), `kinhold-2026-11-07.ged`.

Built: project skeleton, shared theme, a zoomable focus-person tree view (`ui/TreeCanvas.kt`, `tree/FocusLayout.kt`), real storage with add, edit and delete (0.2.0), and backup, restore and undo (0.3.0).
**Backup, restore and undo (0.3.0, checked on the S22):** `model/Backup.kt` is the backup file: one JSON document (`format` "kinhold-backup", `version` 1, `created`, `people`, `parentLinks`, `partnerships`), pure Kotlin apart from `org.json`. `BackupCodec.decode` checks everything before the tree is touched and throws a `BackupException` with a plain-language message for: not JSON or not a backup, a newer version, duplicate ids, a missing or non-numeric id, years outside 0 to 9999, links to people not in the file or to oneself, and any cut-short file; unknown fields are ignored so older apps can read newer files of the same version. `FamilyRepository.replaceAll` replaces the whole tree in one transaction after writing a safety copy of the current tree (`files/safety-before-restore.json`, written to a temp file and renamed); `undoRestore` swaps the two trees back and forth. `deletePerson` returns a `DeletedPerson` and `restoreDeleted` puts the person back with the same id and the links to relatives who still exist; the tree screen shows "Deleted X · Undo" for 10 seconds. Files are saved and opened through the system file picker (no storage permission): `ui/BackupScreen.kt`, `KinholdViewModel.saveBackup/readBackup/restore`. The tree screen shows "Backed up today" or "Not backed up yet" (amber after 5 people with no backup for 30 days). The backup file is not encrypted (the screen says so).
Tests added: 11 JVM tests of the backup file (round trip of 300 people, unicode and quotes, every kind of damaged file, a file cut at six lengths, unknown fields) and 7 more on-phone tests (undo delete, restore replaces and keeps a safety copy, undo swaps back, a restore that fails halfway changes nothing even on disk, a 1,000-person backup restores exactly, new ids after a restore do not clash). Tables: `person`, `parent_link` (child, parent), `partnership` (a_id < b_id). Deleting a person cascades to their links and keeps relatives. Years are optional integers. Screens (`ui/App.kt` switches between them, saved across rotation): `StartScreen` (empty tree: add first person, or load a sample family of 60 to 3,000 people for testing), `TreeScreen` (focus card with Edit, + Parent, + Spouse, + Child), `PersonFormScreen` (name, sex, years, places, notes; delete asks first). ## Sharing, stage 1 done (2026-11-07): permanent person ids (database version 4, backup format version 4)
Every person has a `uid` (random lower-case UUID text, `PersonUid`), created when they are first stored and never changed by editing. `FamilyDb.onUpgrade` (below 4) adds the column, gives everyone already stored an id and adds a unique index. Backup version 4 carries `uid` (older files read fine; the person gets an id when stored; a malformed or repeated id is refused as damaged). Restore, Undo restore and Delete + Undo keep ids. GEDCOM writes `_UID` and reads `_UID` or `UID` when it is a valid, unique UUID. Adding a file (`addAll`) keeps an incoming id unless that id is already in the tree, in which case the copy gets a new one. No screen shows ids yet. ## Sharing, stages 2 to 4 built (2026-11-07), NOT yet run on the phone
- **Export a branch:** `model/Share.kt` (`ShareScope`, `Share.select`, `subFamily`, `subDetails`) picks a person's ancestors, descendants or both, a number of generations (0 = all), spouses, optional "leave out people who may be alive" (no death date and born in the last 110 years; people with no dates are kept; the root is always kept) and photos. `FamilyRepository.exportShare` writes it in the ordinary backup format, so any Kinhold can read it. UI: `ui/ShareScreen.kt`, reached by "Share branch" on the Details page (`Screen.Share`).
- **Merge a file:** `model/Merge.kt` (pure Kotlin) compares an incoming file (share file, backup or GEDCOM, found by its first character) with the tree. Same person by permanent id for sure; otherwise suggestions scored by name (accents and case ignored), birth year (within one), sex, death year and relatives in common (strong at score 4 or more, e.g. same name and birth year; weaker ones are only offered, one-to-one). `fieldChanges` lists every differing field (first names, surname, sex, birth and death date, birth and death place, notes, photo), a fill where yours is empty or less exact, a conflict where both differ. `resolve(accepted, useHis, addEvents)` returns what to do: new people, links (at most two parents per child, extra ones counted as skipped), partnerships, events and sources not already present (compared by kind, detail, date and place), field updates and photo fills. `FamilyRepository.planMerge` and `applyMerge` (one transaction, safety copy first, comparison made again inside it, so Undo works and a failure changes nothing). New people keep the file's permanent id unless it is already in the tree. UI: `ui/MergeScreen.kt` (suggestions with Same person or Different person, each differing field with Keep mine or Use theirs, an events switch, a summary, and Undo this merge afterwards), started from the new "Merge a shared file" card on the Backup screen; the session lives in the view model (`mergeSession`) so rotation does not lose the file, but the choices reset.
- **Help:** new "Sharing with relatives" page with limits. **Tests:** JVM `MergeTest` (21) all pass, 140 JVM tests in all. On-phone `MergeDbTest` (5) and `PersonUidDbTest` (8) are written and compile but have NOT been run (the S22 was not connected). Run `./gradlew :app:connectedDebugAndroidTest` with `ANDROID_SERIAL=R5CT40PGEHF`, then `adb install -r` again, and drive the Share and Merge screens by hand (two test trees: use `docs/test-family-events.ged` as the incoming file and a hand-typed tree).
- **Known limits:** matching is repeated at each merge (a hand-confirmed match between differently-numbered people is not remembered, but once both copies carry the same permanent id it is exact); the choices on the review screen reset on rotation; a large merge lists every differing field in one list; "Fill all my empty fields" and "Keep everything of mine" are the only bulk choices; merging never deletes anything.

## Contact details, "this is me", icons (2026-11-07), built but NOT yet run on the phone (database version 5, backup format version 5)
- **Data:** each person has `address` (500 characters), `phone` (40), an optional saved map pin (`lat`, `lng`, validated, stored as `geo_lat` and `geo_lng`) and `isMe` (column `is_me`, at most one person, set by `FamilyRepository.setMe`). Migration: `FamilyDb.onUpgrade` below 5. Backup version 5 carries them (`address`, `phone`, `lat` and `lng` together, `me`; a lone latitude, an out-of-range pin or two owners is refused as damaged). GEDCOM reads and writes `ADDR` (also the structured ADR1, CITY, POST, CTRY form), `PHON` and a private `_PIN` line; `_ME` is never written. Merge offers Address, Phone number and Map pin as fields like the rest. Share files leave out address, phone, pin and the me mark unless "Address and phone" is switched on (`ShareScope.withContact`; the me mark is never sent). Restore, Undo restore and Delete + Undo keep the me mark.
- **Pins:** `GeoPin.parse` reads plain coordinates, `geo:` links and long Google Maps links (`@lat,lng`, `!3d..!4d..`, `?q=lat,lng`); short links (maps.app.goo.gl) hold no coordinates and are refused with a message. No lookup of addresses, no in-app map, no Google API (paid and needs the internet permission, so left out on purpose).
- **Buttons:** `ui/Actions.kt` builds intents only (no permission): Call (dialler), Text (messages), WhatsApp (`wa.me`, needs a number with country code, otherwise a notice), Map (`geo:` link for the pin or a search of the address). They show on the Details page; the form has the fields and an "open in maps" button.
- **Me:** "This is me" on the Details page; the tree opens on that person and a "Me" button (first in the chip row) returns to them, or explains how to set it.
- **Icons:** `Pill` takes an optional icon (Material core icons, no new dependency); added to the tree chips, focus card, Details page and contact buttons.
- **Not decided or not built:** the navigation home for Settings and tools (a bottom bar was proposed, waiting for the owner), map view and radius search (needs coordinates for every place; paid map APIs are left for later by the owner's decision), several phone numbers or addresses per person, Settings and Backup icons.
- **Tests:** JVM `ContactTest` (all pass, JVM total 156). On-phone `ContactDbTest` (5, includes the version 4 to 5 upgrade) is written and compiles but has NOT been run, like `MergeDbTest` and `PersonUidDbTest`: the S22 was not connected.

## Rule: never run the connected tests without saving the owner's data first (set 2026-11-07, after a wipe)
`./gradlew :app:connectedDebugAndroidTest` uninstalls the app and deletes the tree on the phone, and there is no cloud copy. On 2026-11-07 a test run wiped data the owner had entered. Before any connected test run: tell the owner, ask them to save a backup file from the Backup screen (or run `scripts/phone-backup.sh`, which copies the database off with `run-as`), run the tests, `adb install -r` the app, then restore (the owner's backup file through Restore, or `scripts/phone-restore.sh`). Never run them when the phone's tree has not been saved. An automatic backup is now the top priority feature because of this.

**Tooling notes learned the hard way:**
- adb is at `$LOCALAPPDATA/Android/Sdk/platform-tools/adb.exe` (not on PATH). Use `exec-out screencap -p > file`, `uiautomator dump` and `exec-out cat /sdcard/u.xml`; never `adb pull` into a Git Bash `/tmp` path. Do not press Back more than the app's own depth: it leaves Kinhold and lands in the owner's other apps.
- In the Bash tool, `sed -i "…a\\ …"` with several continuation lines collapses them into one line (it once commented out a whole block), and a heredoc with an apostrophe can fail to parse. Write multi-line code with the Write tool, then splice it in with `head`, `tail` and `cat`.
- `./gradlew :app:compileDebugKotlin` is the fast check; `./gradlew :app:testDebugUnitTest :app:assembleDebug` before installing with `adb install -r` (never uninstall: it deletes the tree).
- The test phone currently holds a 3,000-person invented sample tree, set up for testing; there is no real data on it.
