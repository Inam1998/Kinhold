# Kinhold: start here

Native Android app (Kotlin, Jetpack Compose) for building and keeping a private family tree. Working name and brand: **Kinhold**. App ID `com.inamibrahim.kinhold` (permanent once published). Owner GitHub: Inam1998, repo `Kinhold`.

The full plan, research and monetization are in `docs/PLAN.md`. Read it before starting a feature.

## What it is
A family tree app for people who want to keep their own tree without a subscription. It is free with light ads plus a one-time Pro unlock. It is not a records search service and has no DNA or historical record database. The gap it targets: the big apps (Ancestry 4.0, MyHeritage 3.8, FamilySearch 3.5, all 10M+ downloads) are disliked for price, billing traps, lost trees and a clumsy tree view, while the small apps are basic.

## Rules that must hold
- **Look:** follow `D:\Android Projects\DESIGN-SYSTEM.md` (dark-first navy, cards, big radii, Inter font, gradient glow, floating nav). Only the accent differs: Kinhold is green. Reference code: `ui/Theme.kt` and `ui/Components.kt`.
- **Design for all phones:** old and slow phones count as much as new ones (minSdk 26). Bound memory per item, keep main-thread work independent of tree size, and say in replies what was reasoned for weak phones rather than measured.
- **Never lose a tree.** Data safety is the selling point. Local storage first, atomic saves, automatic backup, GEDCOM and full-file export. Any change that touches stored data needs a migration and a test.
- **Permissions only when a feature needs them,** each disclosed in the store listing: camera (scan), microphone (stories), contacts (import), internet (ads, only when ads are added). Check the manifest before each release.
- **No face recognition** in version 1 (privacy and policy risk).
- **Ads never appear** over the tree view, while editing a person or while recording. Pro removes ads.
- **Every new feature gets a page in the in-app Help guide** in the same change, with its limits stated (`model/HelpGuide.kt`: add a `HelpTopic` and a `HelpPage`; `HelpGuideTest` fails if a topic has no page, if a page does not state its limits, or if the Privacy page says there is no internet permission while the manifest asks for one). When a feature changes, change its page in the same change.
- Commit and push only when the owner asks. Work on a branch, not `main`. Do not put assistant or AI mentions in commits, code or docs.
- Keep this file and `docs/PLAN.md` current when a feature lands.

## Build and test

```bash
cd android
export JAVA_HOME="C:/Program Files/Android/Android Studio/jbr"
./gradlew :app:testDebugUnitTest :app:assembleDebug
```

Phone: Samsung S22 (adb serial `R5CT40PGEHF`, the only test phone). In Git Bash set `MSYS_NO_PATHCONV=1` and wrap adb in `timeout`. Tell the owner before driving the phone.

## Status (2026-11-07, version 0.1.0)
Versioning: nothing has been released, so the app was reset to **0.1.0** (versionCode 1). The 0.2.0 to 0.9.0 labels used below are earlier development stages, not shipped versions. Release APKs go in `D:Android App ReleasesKinhold` only when the owner asks; version bumps happen only when the owner says so.
**Events and sources (0.1.0, database version 3, backup format version 3):** `model/Events.kt` has `PartialDate` (year, month, day, each optional; a month needs a year, a day needs a month), `EventKind` (baptism, burial, occupation, military, residence, immigration and more, plus couple kinds marriage, engagement, divorce, annulment, and Other with a name), `Event`, `Source` (title, citation, note; plain text, no scans) and the limits (500 events per person or couple, 50 sources per event or person, text cut at set lengths). Birth and death keep `born`/`died` years and gain optional month and day columns. Other events are rows in `event` (owned by a person, or by a couple via a composite key to `partnership`), citations rows in `source`; both cascade on delete. `Family` keeps only a small `CoupleInfo` per couple (earliest marriage date, ended or not), so `Family.spousesInOrder` orders spouses by marriage date, then birth year, then id (used by the layout and the add-child chooser), and `Relatives` ignores spouses whose partnership has a divorce or annulment. Events are read per person (`FamilyRepository.details`), never for the whole tree. Migration: `FamilyDb.onUpgrade` for version below 3 adds the four columns and the tables (tests: `EventsDbTest.aVersionTwoDatabaseIsUpgradedWithoutLosingAnything`, and the old version-1 test in `PhotoTest`). Backup: `BackupCodec` version 3 writes `events`, `sources`, month and day fields per person and a top-level `coupleEvents`; versions 1 and 2 still read; impossible dates, over-limit lists and couple events for a couple not in the file are refused as damaged. The safety copy, Undo restore and Delete + Undo carry events and sources. GEDCOM: full dates and events (BAPM, BURI, OCCU, RESI, EVEN with TYPE and so on, MARR, DIV, ENGA, ANUL on couples) and source citations (records with TITL, citations with PAGE and NOTE) are read and written; `GedcomReport` now counts only what is dropped (`datesSimplified` for about/between dates, SSN, ordinances and contact lines as events, family-level citations, events over the limit or on a one-parent family) and says how many events and citations were kept. Citations on a birth or death become person-level sources with an "About the birth." note. UI: the person form has day/month/year boxes, an Events list, marriage events under each spouse, and sources; the event editor (`ui/EventEditor.kt`) is a full screen; the new Details page (`ui/PersonPage.kt`, "Details" button on the focus card) lists everything for one person. Form drafts survive rotation. Help: new "Events, marriages and sources" page, other pages updated. Tests: 112 JVM, 44 on-phone, all passing. By hand on the S22: filled the form including a full birth date, added a Baptism event, saved, and saw it on the Details page; adding a source text in the editor works. Not done or not checked on the phone: marriage and divorce through the UI, a real Ancestry/MyHeritage export, slow-phone behaviour (reasoned: the event list is a lazy list and only one person's events are read, not measured). Limits: no "about" or "between" dates, no scans, events are not drawn on tree cards, a widowed partner does not end a partnership.
**Siblings, half and step relatives (0.8.0, checked on the S22):** `model/Relatives.kt` (`Family.relativesOf`) works out siblings (same recorded parents), half-siblings (some shared), step-parents (a parent's spouse who is not a parent), step-siblings and stepchildren from the existing links, so nothing new is stored and no migration, backup or GEDCOM change was needed. The focus card shows them as tappable cards (tap moves the focus); at most 30. Six JVM tests (`RelativesTest`). On the phone: added a second spouse and a child with her to a person, and the earlier child showed the new child as a half-sibling and her as stepmother. Limits (also on the Help page): adopted, foster and step link types are not recorded; a person with one recorded parent shows all who share that parent as full siblings; couples have no end date, so a parent's former partner shows as a step-parent; relatives are listed, not drawn. Still open from the old list: the layout still allows at most two parents per child.
**Settings (0.7.0, checked on the S22):** `ui/SettingsScreen.kt` (reached by the Settings pill on the tree and start screens) sets the theme (Dark, Light, Phone) and one of six accent colours. `ui/AppSettings.kt` keeps them in a small preferences file (`kinhold-settings`), loaded in `MainActivity` before anything draws, so they are not part of the tree database or backups. The status and navigation bar icons follow the theme. Light theme and the Violet accent were looked at on the phone (tree, focus card, settings) and are readable; the other accents and the remaining screens in Light have not been looked at. The Help guide has a Settings page. Not tested: an automated test of saving the settings.
**Photos and new look (0.6.0, checked on the S22):** each person can have a photo, chosen with the system photo picker (no storage permission). `data/Photos.kt` (`PhotoCodec`) shrinks it to 720 px on the long side (EXIF rotation applied, JPEG q82) and makes a 256 px square thumbnail; both live in a `photo` table (database version 2, with an `onUpgrade` step and a test that upgrades a version-1 file). `Person.photoStamp` changes whenever the photo does; `ui/Avatar.kt` has `AvatarCache` (LRU of 160 thumbnails, stamp-aware) and draws a default head-and-shoulders avatar (blue, rose or grey by sex) for people without a photo. Backups are now format version 2 and carry photos as Base64 (version 1 files still read; GEDCOM does not carry photos). Delete + Undo and Undo restore keep photos. Look: tree cards are larger (176 x 64) with soft shadows, an avatar and a glowing focus ring; start screen has a gradient hero card; buttons shrink slightly when pressed. Help guide has a Photos page. Tests: 87 JVM and 29 on-phone. Frame times with the new cards (10 scripted pan swipes): median 12 ms, 95th 15 ms, 5.4% janky. Limits: no camera capture, photo choice is not kept across rotation of the form, big photo collections make big backups, long names are cut with an ellipsis on the cards. Lesson: never screenshot the system photo picker (it shows the owner's gallery); read it with `uiautomator dump`.
**Help guide (0.5.0):** `ui/HelpScreen.kt` shows eight topics (Getting started, Finding your way around, Adding and editing people, Deleting and undoing, Backups, Restoring, GEDCOM, Privacy), reached from the Help button on the tree screen and "How Kinhold works" on the start screen; each page ends with a "Good to know" card of limits. The built app asks for no internet permission (checked with `aapt2 dump permissions`). When ads or sync are added, the Privacy page, the store listing and the Data safety form must change together (the test fails first).
**Several spouses (0.5.0, checked on the S22):** the layout (`tree/TreeLayout.kt`) works on `UnitNode` (a person, their spouses, and `ChildGroup`s of children by the other parent). The person stands in the middle of their spouses: first spouse to the right, second to the left, third further right, and so on, ordered by spouse birth year then id (marriage dates are not recorded). Each marriage's children are a group placed in the same left-to-right order as the couples, hanging from that couple's own line, with the lines at slightly different heights; a spouse who is not next to the person is joined by a line under the boxes; children whose other parent is not a spouse hang from the person alone. `Relation.ChildOf(parentId, otherParentId)` says who the other parent is: with one spouse the child is theirs automatically, with several a dialog asks "Who is the other parent?" (with an "Only X" choice). Tests: 10 layout tests (spouse order, groups in order, the line under the boxes, random families with many marriages never overlap for any focus, under 10 ms per layout). Totals: 84 JVM and 18 on-phone tests. By hand on the S22: imported a file with a two-marriage person, added a child through the chooser, and added a third spouse.
**GEDCOM import and export (0.4.0, checked on the S22):** `model/Gedcom.kt` (pure Kotlin) reads GEDCOM 5.5, 5.5.1 and the common parts of 7.0, and writes 5.5.1 (UTF-8, CR LF, HEAD with SUBM, lines under 255 characters using CONC and CONT). Reading is forgiving: any line ending, blank or junk lines skipped, UTF-8 with or without BOM, UTF-16 (BOM or not), "ANSI"/ASCII/ANSEL read as Windows-1252 (ANSEL accents in very old files can come out wrong), unmarked non-UTF-8 files fall back to Windows-1252, `@@` unescaped, notes as inline text or as separate NOTE/SNOTE records, `NAME` with `/surname/` and suffix or `GIVN`/`SURN`, dates in every common style reduced to the first year found (`BC` dates give no year), `FAMC` honoured when a family does not list the child, `@VOID@` ignored, several marriages kept as several partnerships. What is not kept is counted in a `GedcomReport` and shown before import: dates with more than a year, events (marriages, jobs, residences and so on), source citations, photos and files, other details, and links to people missing from the file. Export writes one FAM per couple and per group of children with the same parents (couples without children and single parents are kept; a child with more than two parents gets one FAM per parent). Import asks Add (renumbers people, keeps everyone already there; people in both appear twice) or Replace, both writing the safety copy so "Undo the last restore or import" works; an empty tree just offers Import, from the start screen or the Backup screen. Tests: 27 GEDCOM tests (hand-written sample with two marriages, every date and name style, encodings, damaged and random files never crash, 300-person round trip, difficult text, 3,000 people under 3 s) and 2 more on-phone tests (add import with overlapping ids and undo; GEDCOM through the database). Totals: 67 JVM and 18 on-phone tests. By hand on the S22: imported an Ancestry-style file through the picker (dialog counts matched the file), checked the tree, exported it again (`kinhold-2026-11-07.ged` keeps its extension). Test files left on the phone in Downloads: `test-tree.ged` (11 invented people), `kinhold-2026-11-07.ged`.
**Limits:** years only (no day or month), no events, sources or photos, `PEDI` types (adopted, foster) are read as ordinary parent links, no matching of people who are in both the file and the tree, not tried on a real export from Ancestry, MyHeritage or FamilySearch (only on a file written to look like one).
Built: project skeleton, shared theme, a zoomable focus-person tree view (`ui/TreeCanvas.kt`, `tree/FocusLayout.kt`), real storage with add, edit and delete (0.2.0), and backup, restore and undo (0.3.0).
**Backup, restore and undo (0.3.0, checked on the S22):** `model/Backup.kt` is the backup file: one JSON document (`format` "kinhold-backup", `version` 1, `created`, `people`, `parentLinks`, `partnerships`), pure Kotlin apart from `org.json`. `BackupCodec.decode` checks everything before the tree is touched and throws a `BackupException` with a plain-language message for: not JSON or not a backup, a newer version, duplicate ids, a missing or non-numeric id, years outside 0 to 9999, links to people not in the file or to oneself, and any cut-short file; unknown fields are ignored so older apps can read newer files of the same version. `FamilyRepository.replaceAll` replaces the whole tree in one transaction after writing a safety copy of the current tree (`files/safety-before-restore.json`, written to a temp file and renamed); `undoRestore` swaps the two trees back and forth. `deletePerson` returns a `DeletedPerson` and `restoreDeleted` puts the person back with the same id and the links to relatives who still exist; the tree screen shows "Deleted X · Undo" for 10 seconds. Files are saved and opened through the system file picker (no storage permission): `ui/BackupScreen.kt`, `KinholdViewModel.saveBackup/readBackup/restore`. The tree screen shows "Backed up today" or "Not backed up yet" (amber after 5 people with no backup for 30 days). The backup file is not encrypted (the screen says so).
Tests added: 11 JVM tests of the backup file (round trip of 300 people, unicode and quotes, every kind of damaged file, a file cut at six lengths, unknown fields) and 7 more on-phone tests (undo delete, restore replaces and keeps a safety copy, undo swaps back, a restore that fails halfway changes nothing even on disk, a 1,000-person backup restores exactly, new ids after a restore do not clash). Totals: 40 JVM and 16 on-phone tests. Driven by hand on the S22 through the real file picker: save a backup to Downloads, delete and undo, delete for good, restore (dialog said 60 vs 59 people), undo the restore, and choosing a text file (refused with "This file is not a Kinhold backup.").
Phone-driving tip: the system file picker can be driven with `uiautomator dump`; its save button reads "SAVE" in capitals. Test files left on the phone in Downloads: `kinhold-backup-2026-11-07.json` (60 invented people) and `not-a-backup.json`.
**Storage and editing (0.2.0, checked on the S22):** the tree lives in SQLite (`data/FamilyDb.kt`, file `kinhold.db`, version 1, write-ahead logging, foreign keys on). `data/FamilyRepository.kt` is the only thing that writes it: every change runs in one transaction, then a new immutable `model/Family` snapshot is published as a `StateFlow`; `data/KinholdViewModel.kt` runs it off the main thread. Tables: `person`, `parent_link` (child, parent), `partnership` (a_id < b_id). Deleting a person cascades to their links and keeps relatives. Years are optional integers. Screens (`ui/App.kt` switches between them, saved across rotation): `StartScreen` (empty tree: add first person, or load a sample family of 60 to 3,000 people for testing), `TreeScreen` (focus card with Edit, + Parent, + Spouse, + Child), `PersonFormScreen` (name, sex, years, places, notes; delete asks first). A child gets the father's surname and a spouse the opposite sex as starting values; the focus stays on the person you added a relative to.
Tests: 29 JVM unit tests (`app/src/test`) and 9 on-phone tests of the real database (`app/src/androidTest/.../FamilyRepositoryTest.kt`, run with `./gradlew :app:connectedDebugAndroidTest` and `ANDROID_SERIAL=R5CT40PGEHF`; they use in-memory or throwaway databases, but the run uninstalls the app afterwards, which clears the stored tree, so reinstall with `adb install -r`). Covered: all fields round-trip, parent/child/spouse links, two parents become a couple, a failed save rolls back completely, delete cascade, sample import once only, and the tree surviving a close and reopen. Also seen working by hand on the S22: first person, add child, kill and relaunch (data kept), edit form, delete confirm and delete.
**Not done:** no migration step exists yet (version 1 is the first format; the first change to the schema needs a step in `onUpgrade` and a test), no automatic backup (the user must save a file; the app only reminds), no photos. Android Auto Backup is off (`allowBackup="false"`); turning it on would put the tree in the user's Google backup, which changes the "kept on this phone" wording, so it is the owner's call.
**Tried on the S22 (2026-11-07, `dumpsys gfxinfo` after 10 scripted pan swipes; pinch and tap not tested):** 1,000 people: median 12 ms, 95th 15 ms, 3.9% janky; 3,000 people (start view): median 12 ms, 95th 19 ms, 3.2% janky; 3,000 "Fit all": median 15 ms, 7.3% janky; 60 people fit: median 11 ms. The S22 is the fastest phone we have, and a median of 11 to 15 ms with only about 15 cards on screen means a fixed per-frame cost that has not been profiled; on a phone several times slower this will stutter. Profile before optimising.
**Layout finding:** a full top-down tree is far too wide to overview (60 people "Fit all" was an unreadable sliver, 3,000 a single line), so the main view is now a focus-person view.
**Focus view (built 2026-11-07, 17 unit tests pass, seen on the S22):** `tree/FocusLayout.kt` draws 3 rows of ancestors above, the focused person with their first spouse, and 2 rows of descendants below, so the cost depends on those depths and not on the size of the tree. `model/Family.kt` answers parents, spouses and children for anyone and searches by name. Tap a card to move the focus to that person; green "+N" pills mark children not drawn and a small arrow marks ancestors not drawn; "Find" searches by name, "Oldest" jumps to the oldest person, "Recenter" reframes. Checked on the S22 by adb: tap to refocus, Find (opens above the keyboard, picks a result), and fling after a drag (a horizontal 80 ms flick gives about 125 frames, about one second of glide; vertical flicks give fewer frames because the tree stops at its edge). Pinch cannot be driven by adb and has not been tried. Frame times in the focus view, 10 scripted pan swipes: 300 people median 12 ms, 99th 17 ms, 6% janky; 3,000 people median 11 ms, 99th 16 ms, 5.3% janky, so they do not depend on tree size. Giving the canvas its own graphics layer did not change the median, so the fixed per-frame cost of about 11 to 12 ms is not the header redrawing; suspects are the two full-screen radial gradients on the GPU and input dispatch. Profile (Perfetto or `adb shell dumpsys gfxinfo ... framestats`) before optimising, and judge on a slower phone.
Gotcha: in `adb` tests the chip row scrolls, so tap coordinates move; use `uiautomator dump` and read the `content-desc` bounds of each pill instead of fixed coordinates.
Known gaps: step and half relations are not modelled (a child has at most two parents), a spouse's own other marriages and parents are not drawn (refocus on that spouse to see them), test data only.

## Next feature (decided with the owner 2026-11-07): sharing trees between people
Each person builds their own tree and can send part of it to a relative. Design: a permanent random ID per person (migration, backup format change, tests); a Kinhold share file (not GEDCOM) exported from one person with a scope (ancestors, descendants or both, number of generations, spouses, photos, optional "exclude living people"); an import review screen with three groups (same person by ID = merged, possible match by name, birth date and relatives = the owner decides, new = added); conflicts are asked per person and per field, never silently overwritten; the existing safety copy gives Undo. No internet permission. Stages: IDs and migration, export from a person, match and review import, Help page and tests. Test file with events: `docs/test-family-events.ged` (invented family: a divorce and a second marriage).
