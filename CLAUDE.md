# Kinhold: start here

Native Android app (Kotlin, Jetpack Compose) for building and keeping a private family tree. Working name and brand: **Kinhold**. App ID `com.inamibrahim.kinhold` (permanent once published). Owner GitHub: Inam1998, repo `Kinhold`.

The full plan, research and monetization are in `docs/PLAN.md`. Read it before starting a feature.

## What it is
A family tree app for people who want to keep their own tree without a subscription. It is free with light ads plus a one-time Pro unlock. It is not a records search service and has no DNA or historical record database. The gap it targets: the big apps (Ancestry 4.0, MyHeritage 3.8, FamilySearch 3.5, all 10M+ downloads) are disliked for price, billing traps, lost trees and a clumsy tree view, while the small apps are basic.

## Rules that must hold
- **Look:** follow `D:\Android Projects\DESIGN-SYSTEM.md` (dark-first navy, cards, big radii, Inter font, gradient glow, floating nav). Only the accent differs: Kinhold is green. Reference code: `ui/Theme.kt` and `ui/Components.kt`.
- **Design for all phones:** old and slow phones count as much as new ones (minSdk 26). Bound memory per item, keep main-thread work independent of tree size, and say in replies what was reasoned for weak phones rather than measured.
- **Never lose a tree.** Data safety is the selling point. Local storage first, atomic saves, automatic backup, GEDCOM and full-file export. Any change that touches stored data needs a migration and a test.
- **Permissions only when a feature needs them,** each disclosed in the store listing: camera (scan), microphone (stories), contacts (import), internet (ads, only when ads are added). Check the manifest before each release.
- **No face recognition** in version 1 (privacy and policy risk).
- **Ads never appear** over the tree view, while editing a person or while recording. Pro removes ads.
- **Every new feature gets a page in the in-app Help guide** in the same change, with its limits stated (to be created with the first real feature).
- Commit and push only when the owner asks. Work on a branch, not `main`. Do not put assistant or AI mentions in commits, code or docs.
- Keep this file and `docs/PLAN.md` current when a feature lands.

```bash
cd android
export JAVA_HOME="C:/Program Files/Android/Android Studio/jbr"
./gradlew :app:testDebugUnitTest :app:assembleDebug
```
APK: `android/app/build/outputs/apk/debug/app-debug.apk`. Do not copy builds into a releases folder until the owner asks. Phone: Samsung S22 (adb serial `R5CT40PGEHF`, the only test phone). In Git Bash set `MSYS_NO_PATHCONV=1` and wrap adb in `timeout`. Tell the owner before driving the phone.

## Status (2026-11-07, version 0.4.0)
**GEDCOM import and export (0.4.0, checked on the S22):** `model/Gedcom.kt` (pure Kotlin) reads GEDCOM 5.5, 5.5.1 and the common parts of 7.0, and writes 5.5.1 (UTF-8, CR LF, HEAD with SUBM, lines under 255 characters using CONC and CONT). Reading is forgiving: any line ending, blank or junk lines skipped, UTF-8 with or without BOM, UTF-16 (BOM or not), "ANSI"/ASCII/ANSEL read as Windows-1252 (ANSEL accents in very old files can come out wrong), unmarked non-UTF-8 files fall back to Windows-1252, `@@` unescaped, notes as inline text or as separate NOTE/SNOTE records, `NAME` with `/surname/` and suffix or `GIVN`/`SURN`, dates in every common style reduced to the first year found (`BC` dates give no year), `FAMC` honoured when a family does not list the child, `@VOID@` ignored, several marriages kept as several partnerships. What is not kept is counted in a `GedcomReport` and shown before import: dates with more than a year, events (marriages, jobs, residences and so on), source citations, photos and files, other details, and links to people missing from the file. Export writes one FAM per couple and per group of children with the same parents (couples without children and single parents are kept; a child with more than two parents gets one FAM per parent). Import asks Add (renumbers people, keeps everyone already there; people in both appear twice) or Replace, both writing the safety copy so "Undo the last restore or import" works; an empty tree just offers Import, from the start screen or the Backup screen. Tests: 27 GEDCOM tests (hand-written sample with two marriages, every date and name style, encodings, damaged and random files never crash, 300-person round trip, difficult text, 3,000 people under 3 s) and 2 more on-phone tests (add import with overlapping ids and undo; GEDCOM through the database). Totals: 67 JVM and 18 on-phone tests. By hand on the S22: imported an Ancestry-style file through the picker (dialog counts matched the file), checked the tree, exported it again (`kinhold-2026-11-07.ged` keeps its extension). Test files left on the phone in Downloads: `test-tree.ged` (11 invented people), `kinhold-2026-11-07.ged`.
**Limits:** years only (no day or month), no events, sources or photos, `PEDI` types (adopted, foster) are read as ordinary parent links, only the first spouse is drawn although all are stored, no matching of people who are in both the file and the tree, not tried on a real export from Ancestry, MyHeritage or FamilySearch (only on a file written to look like one).
Built: project skeleton, shared theme, a zoomable focus-person tree view (`ui/TreeCanvas.kt`, `tree/FocusLayout.kt`), real storage with add, edit and delete (0.2.0), and backup, restore and undo (0.3.0).
**Backup, restore and undo (0.3.0, checked on the S22):** `model/Backup.kt` is the backup file: one JSON document (`format` "kinhold-backup", `version` 1, `created`, `people`, `parentLinks`, `partnerships`), pure Kotlin apart from `org.json`. `BackupCodec.decode` checks everything before the tree is touched and throws a `BackupException` with a plain-language message for: not JSON or not a backup, a newer version, duplicate ids, a missing or non-numeric id, years outside 0 to 9999, links to people not in the file or to oneself, and any cut-short file; unknown fields are ignored so older apps can read newer files of the same version. `FamilyRepository.replaceAll` replaces the whole tree in one transaction after writing a safety copy of the current tree (`files/safety-before-restore.json`, written to a temp file and renamed); `undoRestore` swaps the two trees back and forth. `deletePerson` returns a `DeletedPerson` and `restoreDeleted` puts the person back with the same id and the links to relatives who still exist; the tree screen shows "Deleted X · Undo" for 10 seconds. Files are saved and opened through the system file picker (no storage permission): `ui/BackupScreen.kt`, `KinholdViewModel.saveBackup/readBackup/restore`. The tree screen shows "Backed up today" or "Not backed up yet" (amber after 5 people with no backup for 30 days). The backup file is not encrypted (the screen says so).
Tests added: 11 JVM tests of the backup file (round trip of 300 people, unicode and quotes, every kind of damaged file, a file cut at six lengths, unknown fields) and 7 more on-phone tests (undo delete, restore replaces and keeps a safety copy, undo swaps back, a restore that fails halfway changes nothing even on disk, a 1,000-person backup restores exactly, new ids after a restore do not clash). Totals: 40 JVM and 16 on-phone tests. Driven by hand on the S22 through the real file picker: save a backup to Downloads, delete and undo, delete for good, restore (dialog said 60 vs 59 people), undo the restore, and choosing a text file (refused with "This file is not a Kinhold backup.").
Phone-driving tip: the system file picker can be driven with `uiautomator dump`; its save button reads "SAVE" in capitals. Test files left on the phone in Downloads: `kinhold-backup-2026-11-07.json` (60 invented people) and `not-a-backup.json`.
**Storage and editing (0.2.0, checked on the S22):** the tree lives in SQLite (`data/FamilyDb.kt`, file `kinhold.db`, version 1, write-ahead logging, foreign keys on). `data/FamilyRepository.kt` is the only thing that writes it: every change runs in one transaction, then a new immutable `model/Family` snapshot is published as a `StateFlow`; `data/KinholdViewModel.kt` runs it off the main thread. Tables: `person`, `parent_link` (child, parent), `partnership` (a_id < b_id). Deleting a person cascades to their links and keeps relatives. Years are optional integers. Screens (`ui/App.kt` switches between them, saved across rotation): `StartScreen` (empty tree: add first person, or load a sample family of 60 to 3,000 people for testing), `TreeScreen` (focus card with Edit, + Parent, + Spouse, + Child), `PersonFormScreen` (name, sex, years, places, notes; delete asks first). A child gets the father's surname and a spouse the opposite sex as starting values; the focus stays on the person you added a relative to.
Tests: 29 JVM unit tests (`app/src/test`) and 9 on-phone tests of the real database (`app/src/androidTest/.../FamilyRepositoryTest.kt`, run with `./gradlew :app:connectedDebugAndroidTest` and `ANDROID_SERIAL=R5CT40PGEHF`; they use in-memory or throwaway databases, but the run uninstalls the app afterwards, which clears the stored tree, so reinstall with `adb install -r`). Covered: all fields round-trip, parent/child/spouse links, two parents become a couple, a failed save rolls back completely, delete cascade, sample import once only, and the tree surviving a close and reopen. Also seen working by hand on the S22: first person, add child, kill and relaunch (data kept), edit form, delete confirm and delete.
**Not done:** no migration step exists yet (version 1 is the first format; the first change to the schema needs a step in `onUpgrade` and a test), no automatic backup (the user must save a file; the app only reminds), no photos, no multiple spouses, and the in-app Help guide required by the rules does not exist yet. Android Auto Backup is off (`allowBackup="false"`); turning it on would put the tree in the user's Google backup, which changes the "kept on this phone" wording, so it is the owner's call.
**Tried on the S22 (2026-11-07, `dumpsys gfxinfo` after 10 scripted pan swipes; pinch and tap not tested):** 1,000 people: median 12 ms, 95th 15 ms, 3.9% janky; 3,000 people (start view): median 12 ms, 95th 19 ms, 3.2% janky; 3,000 "Fit all": median 15 ms, 7.3% janky; 60 people fit: median 11 ms. The S22 is the fastest phone we have, and a median of 11 to 15 ms with only about 15 cards on screen means a fixed per-frame cost that has not been profiled; on a phone several times slower this will stutter. Profile before optimising.
**Layout finding:** a full top-down tree is far too wide to overview (60 people "Fit all" was an unreadable sliver, 3,000 a single line), so the main view is now a focus-person view.
**Focus view (built 2026-11-07, 17 unit tests pass, seen on the S22):** `tree/FocusLayout.kt` draws 3 rows of ancestors above, the focused person with their first spouse, and 2 rows of descendants below, so the cost depends on those depths and not on the size of the tree. `model/Family.kt` answers parents, spouses and children for anyone and searches by name. Tap a card to move the focus to that person; green "+N" pills mark children not drawn and a small arrow marks ancestors not drawn; "Find" searches by name, "Oldest" jumps to the oldest person, "Recenter" reframes. Checked on the S22 by adb: tap to refocus, Find (opens above the keyboard, picks a result), and fling after a drag (a horizontal 80 ms flick gives about 125 frames, about one second of glide; vertical flicks give fewer frames because the tree stops at its edge). Pinch cannot be driven by adb and has not been tried. Frame times in the focus view, 10 scripted pan swipes: 300 people median 12 ms, 99th 17 ms, 6% janky; 3,000 people median 11 ms, 99th 16 ms, 5.3% janky, so they do not depend on tree size. Giving the canvas its own graphics layer did not change the median, so the fixed per-frame cost of about 11 to 12 ms is not the header redrawing; suspects are the two full-screen radial gradients on the GPU and input dispatch. Profile (Perfetto or `adb shell dumpsys gfxinfo ... framestats`) before optimising, and judge on a slower phone.
Gotcha: in `adb` tests the chip row scrolls, so tap coordinates move; use `uiautomator dump` and read the `content-desc` bounds of each pill instead of fixed coordinates.
Known gaps: only the first spouse is shown (no multiple marriages), step and half relations are not modelled, no spouse's parents are shown (refocus on the spouse to see them), test data only.
